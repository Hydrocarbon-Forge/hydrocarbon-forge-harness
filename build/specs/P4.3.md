## Objective

Implement the Substrate run orchestrator and complete integration scenario suite:
1. Integration scenario battery (`test/integration/scenarios/**`): Written first as protected test fixtures per §14.5 (the 15 scenarios excluding #11 which is scheduled for P6.1), each executing against throwaway git repositories and deterministic fake harnesses (`fake`), testing all lifecycle transitions, failure classes, and edge cases.
2. Effects runner (`src/engine/effects.ts`): Implements the deterministic effects runner executing pure actions derived from engine state (`nextActions(state, settings)`), dispatching router queries, planner runner sessions, worktree setups with network, sandboxed worker processes, L0 heal resumes, L1/L2 replanning, `git merge-tree` preflights, batch merges, integration verifications, culprit bisection, gate pauses, and process kills.
3. Run orchestrator (`src/engine/engine.ts`): Implements `Engine.run(opts)` and `Engine.resume(run_id, opts)` coordinating the full lifecycle (`CREATED` through `FINISHED`), acquiring run locks (`.substrate/state/<run_id>.lock`), appending events to `EventStore` (`.substrate/runs/<run_id>/events.jsonl`), enforcing run modes (`auto`, `solo`, `plan`), evaluating permission gates (`--permission-mode`), checking cost thresholds, monitoring usage and terminating budget overshoots, and handling abort signals.

## Behavior

The orchestrator and effects runner execute according to the following decision trees:

1. Run initialization and lock acquisition:
   - IF `opts.resume` is specified:
     - THEN Engine locates `.substrate/runs/<resume_id>/events.jsonl`, replays all events via `reduce(state, event)`, acquires run lock, and resumes execution loop.
   - ELSE:
     - Generate unique `run_id` (`r_` + 12 base32 characters).
     - Attempt to acquire run lock `.substrate/state/<run_id>.lock` with current PID and timestamp:
       - IF lock file exists AND PID is active with recent heartbeat:
         - THEN fail immediately with concurrency conflict error.
       - ELSE:
         - Overwrite stale lock and begin periodic heartbeat.
     - Emit `run.created` event into event log.
     - IF `opts.mode === "solo"`:
       - THEN emit `run.routed` with mode `solo`; bypass governor and planner; transition state directly to `SETUP` for single task.
     - ELSE IF `opts.mode === "auto"`:
       - IF `settings.roles.governor.enabled === true` AND governor health check passes:
         - THEN call governor intake tool (`callGovernorIntake`);
         - IF governor recommends `solo`:
           - THEN route as `solo`;
           - ELSE route as `plan`.
       - ELSE:
         - Fall back to rules-first router (`routeRequest`).
     - ELSE (`opts.mode === "plan"`):
       - THEN route to planner via rules-first router (`routeRequest`).

2. Planning, linting, and approval gates:
   - For `plan` mode:
     - Emit `plan.started`.
     - Invoke `runPlanner` within isolated run directory `.substrate/runs/<run_id>/`:
       - IF planner output fails YAML/frontmatter parsing:
         - IF format retries < `settings.budgets.planner_format_retries`:
           - THEN emit format retry hint and retry planner session;
           - ELSE emit `task.failed(spec_invalid)` and fail run (exit 1).
       - Commit contract stubs to run branch `substrate/runs/<run_id>` after contract typecheck passes.
       - Emit `plan.produced` and `contracts.committed`.
     - Execute plan linter (`lintPlan` rules L001–L027):
       - IF any error-level diagnostic exists:
         - THEN emit `plan.lint(valid=false)`, emit `plan.rejected`, fail run with exit 1.
       - IF estimated cost > `settings.budgets.approval_threshold_usd` OR `opts.permission_mode === "default"`:
         - IF `opts.permission_mode === "dontAsk"`:
           - THEN emit `run.paused(needs_approval)` and terminate engine with exit code 3.
         - ELSE IF `opts.permission_mode === "plan"`:
           - THEN emit `plan.ready` and terminate engine with exit code 0 (plan-only complete).
         - ELSE IF `opts.permission_mode === "bypassPermissions"`:
           - THEN emit `plan.approved` and transition to `SETUP`.
         - ELSE:
           - Pause engine and await user approval (`run.paused(needs_approval)`).
       - ELSE:
         - Emit `plan.approved` and transition to `SETUP`.

3. DAG scheduling and concurrent worker execution:
   - Compute DAG layers from task specs (`computeDagLayers`).
   - For each dependency batch:
     - Emit `batch.started`.
     - Schedule ready tasks up to `settings.concurrency.workers`.
     - For each task in batch:
       - Create isolated task worktree under `.substrate/worktrees/<run_id>-<task_id>-g<gen>`.
       - Execute `manifest.setup` commands with network access in task worktree; emit `setup.done`.
       - Record pre-execution SHA-256 hashes of all files matching `protected` globs.
       - Spawn worker session with sandbox restrictions (network denied, git commit denied, subagents denied).
       - Monitor stream of backend events:
         - On `usage` event:
           - Update cumulative cost and token counts.
           - IF total cost >= 100% of `budgets.run.max_usd` OR tokens >= `max_tokens`:
             - THEN kill worker process group; emit `run.budget.exceeded`; pause run (`budget_exhausted`, exit 4).
           - ELSE IF total cost >= 80% of `max_usd`:
             - THEN emit `run.budget.warning`.
         - On `error(rate_limit)` event:
           - Back off exponentially; halve concurrency limit (floor 1); pause run if backoff exhausted.
         - On `permission.denied` event:
           - Kill session; emit `run.paused(permission_denied)`; do not replan (exit code 3).
       - On worker session completion:
         - Inspect file modifications against `spec.write` and `spec.create` globs:
           - Revert any paths outside allowed scope.
           - IF out-of-scope files were touched AND `settings.git.on_scope_violation === "fail"`:
             - THEN mark task failed with `scope_violation`.
         - Verify SHA-256 hashes of all `protected` files:
           - IF any hash differs from pre-execution snapshot:
             - THEN mark task failed with `protected_modified`.
         - Execute acceptance commands (`spec.verify`) in sandboxed worktree via verify runner:
           - IF all verify commands exit 0:
             - THEN commit allowed files to task branch with explicit pathspec; mark task `PASSED`.
             - ELSE:
               - IF current attempt === 1:
                 - THEN transition task to `HEALING` (L0); resume worker session with capped failure output tails (<= 8 KB).
                 - ELSE:
                   - Mark task `FAILED` with `verify_failed`.

4. Escalation ladder and replan loop:
   - When a task fails after L0 healing:
     - IF failure class is `permission_denied` OR `rate_limited`:
       - THEN do not trigger replanning; pause run with reason `permission_denied` or `rate_limited`.
     - ELSE:
       - Evaluate escalation ladder (`evaluateEscalation`):
         - IF L1 replan (task generation <= `settings.budgets.l1_replans_per_task`):
           - THEN build `FailurePacket` (`buildFailurePacket`);
           - Invoke planner on escalated model tier from `settings.routing.escalation`;
           - Produce revised task spec at generation `g+1`;
           - Invalidate old worktree; mark task `READY` at generation `g+1`.
         - ELSE IF L2 replan (run L2 count < `settings.budgets.l2_per_run`):
           - THEN invoke planner to amend contracts and manifest stubs;
           - Invalidate all downstream dependent tasks; re-lint amended specs;
           - Resume execution with updated contract baseline.
         - ELSE (L3 escalation):
           - Mark all dependent tasks `BLOCKED`; pause run with `needs_human` (exit code 3).

5. Batch merge, integration verification, and culprit bisection:
   - When all tasks in the current batch reach terminal states (`PASSED`, `BLOCKED`, or `FAILED`):
     - IF any task in the batch failed without successful replan:
       - THEN halt batch progression; mark dependent tasks `BLOCKED`; pause run with `needs_human`.
     - ELSE:
       - For each passed task in deterministic order (topological, then task ID):
         - Run preflight `git merge-tree --write-tree --name-only <run-branch> <task-branch>`.
         - IF merge conflict detected:
           - THEN mark task `FAILED(merge_conflict)`; trigger L1 replan.
           - ELSE:
             - Merge task branch into integration worktree.
       - Execute `manifest.integration_verify` commands across merged integration worktree:
         - IF all integration verify commands exit 0:
           - THEN record run branch checkpoint SHA; emit `batch.merged`; advance to next batch.
         - ELSE (integration verify fails):
           - Revert integration worktree to pre-batch checkpoint.
           - Bisect culprit deterministically: merge tasks one by one and re-run `integration_verify`.
           - The first task whose merge triggers failure is isolated as culprit.
           - Assemble `FailurePacket(integration_failed)` for culprit task.
           - Revert culprit; trigger L1 replan for culprit; keep passing sibling merges.

6. Cancellation and signal handling:
   - IF `opts.signal` triggers abort (SIGINT or SIGTERM):
     - THEN send `SIGTERM` to all active child process groups;
     - Wait grace period (5000ms), then send `SIGKILL` to any surviving processes;
     - Clean up temporary worktrees; release run lock;
     - Emit `run.paused(user_cancel)` or `run.finished` with exit code 130 (SIGINT) or 143 (SIGTERM).

7. The 15 Integration Scenarios (behavioral verification):
   - Scenario 01 (`scenario-01-all-pass.test.ts`): All tasks in DAG layers pass verify on attempt 1, merge cleanly without conflict, pass integration verify, exit 0.
   - Scenario 02 (`scenario-02-heal-pass.test.ts`): Task fails verify attempt 1, L0 resumes worker session with failure tail, passes attempt 2, merges cleanly.
   - Scenario 03 (`scenario-03-double-fail-replan.test.ts`): Task fails attempt 1 and 2, failure packet generated, L1 replans at `g2` on higher tier model, passes, merges.
   - Scenario 04 (`scenario-04-scope-violation-reverted.test.ts`): Worker modifies out-of-scope file; engine reverts change; verification runs on allowed files.
   - Scenario 05 (`scenario-05-protected-modified.test.ts`): Worker tampers with protected test file; hash mismatch detected; task fails with `protected_modified`.
   - Scenario 06 (`scenario-06-permission-denied-pause.test.ts`): Worker triggers tool denial; engine immediately pauses run (`permission_denied`, exit 3); no replanning.
   - Scenario 07 (`scenario-07-budget-kill.test.ts`): Worker cost exceeds `budgets.run.max_usd`; process group killed; run pauses (`budget_exhausted`, exit 4).
   - Scenario 08 (`scenario-08-timeout-kill.test.ts`): Worker exceeds execution timeout; process group killed with SIGKILL; task marked `timeout`.
   - Scenario 09 (`scenario-09-merge-conflict-replan.test.ts`): Two tasks edit same file lines; preflight `git merge-tree` detects conflict; task triggers L1 replan.
   - Scenario 10 (`scenario-10-integration-bisect.test.ts`): Merged batch fails `integration_verify`; engine bisects batch task-by-task to isolate culprit task.
   - Scenario 12 (`scenario-12-rate-limit-backoff.test.ts`): Adapter returns rate limit error; engine backs off, halves concurrency (floor 1), avoids replanning.
   - Scenario 13 (`scenario-13-planner-format-retry.test.ts`): Planner returns invalid format; engine retries up to `planner_format_retries` before succeeding or failing.
   - Scenario 14 (`scenario-14-l2-contract-defect.test.ts`): Contract defect triggers L2; planner amends contract stubs and manifest; dependent tasks re-linted.
   - Scenario 15 (`scenario-15-governor-fallback.test.ts`): Governor service is down or unreachable; engine logs warning and seamlessly falls back to rules router.
   - Scenario 16 (`scenario-16-solo-mode.test.ts`): Engine run in solo mode; planner and manifest bypassed; single worker executed, verified, and committed.

## Invariants

- State derivation purity: Engine state is derived strictly through `reduce(state, event)` and `nextActions(state, settings)`. No other code modifies state.
- Event sourcing truth: `.substrate/runs/<run_id>/events.jsonl` is the sole source of truth; replaying events deterministically restores exact engine state.
- Lock exclusivity: Run lock `.substrate/state/<run_id>.lock` guarantees exactly one engine process operates on a given run directory.
- Worker commit ban: Workers are strictly forbidden from committing; engine commits allowed files using git pathspecs after verification passes.
- Network sandbox isolation: Worker sessions run with network denied; only `manifest.setup` commands execute with network access.
- Budget supremacy: Engine process-group kills enforce USD and token limits at 100% threshold regardless of backend native flag support.
- L0 heal bound: At most one L0 heal resume per task generation; worker never sees or controls attempt counters.
- Escalation ladder bounds: At most `budgets.l1_replans_per_task` (default 2) L1 replans per task; at most `budgets.l2_per_run` (default 2) L2 amendments per run.
- Zero replan on denials: Neither `permission_denied` nor `rate_limited` triggers replanning; they pause the run or back off concurrency.
- Merge-tree non-destructive preflight: Preflight conflict checks via `git merge-tree` never alter working tree or index files.
- Delivery gate required: Run branches are never merged into user working branches without explicit interactive or configured gate approval.

## Edge cases

- Stale run lock recovery: If lock file exists but PID does not exist or heartbeat exceeds timeout, engine warns and claims lock.
- Zero-task plan: When planner generates an empty task list, engine logs completion, sets status `finished`, and exits with code 0.
- All remaining tasks blocked: When a failed task leaves all remaining tasks in `BLOCKED` state, engine halts and exits with code 3 (`needs_human`).
- Base integration failure: If `integration_verify` fails before merging any task, engine flags configuration failure rather than task culprit.
- Torn event log line: Trailing incomplete JSON line in `events.jsonl` from an ungraceful crash is ignored during resume replay.
- Signal during merge operation: Active `git merge-tree` or integration checkout is rolled back cleanly to prior checkpoint before releasing lock.
- Concurrency floor at 1: Rate-limit backoff cannot reduce worker concurrency below 1; if limit persists at concurrency 1, run pauses.
- Worker process crash: Nonzero exit code from worker without structured result is classified as `worker_crashed` and escalated.

## Guardrails

- Never execute git commands (`git push`, `git reset --hard`, `git checkout`) that mutate the user's active branch or untracked workspace files.
- Never grant network access to worker harness processes during task implementation.
- Every child process must be launched in an isolated process group (`detached: true`) to ensure clean tree termination on kill signals.
- Worker LLM transcripts must never be passed to the planner; only capped diffs, test tails, and sanitized summaries are included in failure packets.
- All code blocks across this specification must not exceed 12 lines.

## Out of scope

- Scenario 11 (chaos crash/resume testing at every event boundary): Explicitly deferred to work package P6.1.
- Native subagent dispatcher mode: Engine fans out one process per task; native dispatcher mode is reserved for Phase 7.
- CLI argument parsing and terminal UI rendering: Handled exclusively in Phase 5 (`src/cli/**` and `src/tui/**`).
- Live backend API calls: The 15 integration scenarios execute entirely against throwaway git repos and the deterministic `fake` harness.
