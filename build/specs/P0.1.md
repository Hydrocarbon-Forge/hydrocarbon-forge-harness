## Objective

Establish the repository scaffold so every later work package has declared npm scripts, a compiling TypeScript baseline, a green test runner, and an enforced import-boundary check. Declare all scripts once here; later WPs replace stub bodies without editing `package.json`.

## Interface

- `package.json` exports scripts (each delegating to `scripts/<name>.mjs`) and binary mapping:
  - `typecheck` → `scripts/typecheck.mjs`
  - `test` → `vitest` (config `vitest.config.ts`)
  - `check:boundaries` → `scripts/check-boundaries.mjs`
  - `export-schemas` → `scripts/export-schemas.mjs`
  - `bench` → `scripts/bench.mjs`
  - `docs:check` → `scripts/docs-check.mjs`
  - `bundle` → `scripts/bundle.mjs`
  - `bin: { substrate: bin/substrate.mjs }` → `bin/substrate.mjs` delegating to built CLI (stub for now)
- `tsconfig.json`: strict TypeScript, ESM, Node ≥ 22 configuration.
- `vitest.config.ts`: vitest configuration covering `test/**`.
- `src/index.ts`: package entry point (stub export only, no engine logic).
- `test/smoke.test.ts`: minimal smoke test asserting scaffold loads.
- `scripts/check-boundaries.mjs`: real boundary check per §15 import boundaries.
- `scripts/export-schemas.mjs`, `scripts/bench.mjs`, `scripts/docs-check.mjs`, `scripts/bundle.mjs`: stubs that exit 0 with a notice.
- Copy declarations from SUBSTRATE-PLAN.md Appendix A exactly where referenced; do not invent names.

## Behavior

- If `package.json` is missing required scripts or `bin` entry:
  - Add every script listed in Interface, each delegating to its `scripts/<name>.mjs` file.
  - Add `bin: substrate → bin/substrate.mjs`.
- If `scripts/check-boundaries.mjs` runs:
  - Enforce §15 boundaries: `contracts` and `util` import nothing internal except each other; `backends` imports only `contracts`, `util`; `engine` may import everything except `cli|tui|hooks`; nothing imports `cli|tui`.
  - Exit non-zero on violation; exit 0 when clean.
- If a stub script (`export-schemas`, `bench`, `docs-check`, `bundle`) runs:
  - Print a notice that the real implementation arrives in its owning WP.
  - Exit 0.
- If `npm run typecheck` runs:
  - Typecheck the repo strictly with zero errors.
- If `npm test` runs:
  - Execute `test/smoke.test.ts` green (no other tests exist yet).
- If `npm install` runs:
  - Install declared dependencies (TypeScript strict, ESM, zod, yaml, picomatch, vitest, esbuild per §15 stack as needed by scaffold).

## Invariants

- `package.json` declares every npm script any later Verify column uses; no later WP edits `package.json` except via an explicit replan.
- No implementation bodies for engine, backends, roles, CLI, or TUI in this WP.
- Import boundaries hold on the scaffold and stay green.
- ESM + TypeScript strict throughout; Node ≥ 22.
- No model calls, no network access, no git operations beyond the files in the write set.

## Edge cases

- Fresh checkout with no `node_modules`: `npm install` then all verify commands still pass.
- Node version below minimum: typecheck or install surfaces a clear error; do not silently continue.
- Stub scripts invoked with extra args: ignore args, print notice, still exit 0.
- Boundary checker run on scaffold with only `src/index.ts`: passes trivially (no internal imports to violate).
- `bin/substrate.mjs` invoked before CLI exists: prints stub notice and exits 0 (does not crash).

## Guardrails

- Write only the files listed in frontmatter `write`/`create`; do not create `src/contracts/**`, `src/engine/**`, or any later-WP paths.
- Do not add dependencies beyond what the scaffold needs without a decision-log entry.
- Do not run `git commit/push/checkout/reset/rebase/clean/stash`.
- Do not read or log credentials; secret patterns never appear in scripts or tests.
- Keep the change small (scaffold only, Sz S); prefer minimal config values consistent with §15.

## Out of scope

- Any engine, store, git, verify, backend, role, CLI, TUI, hook, ledger, or config implementation.
- Real bodies for `export-schemas`, `bench`, `docs-check`, `bundle` scripts (owned by P1.1, P6.3, P6.4).
- Contract schemas, JSON Schema export, pricing, routing, settings, agents, or benchmark content.
- Documentation pages, README, reference docs, or packaging beyond the stub `bundle` script.
- Live harness calls, sandboxing, or cost tracking.
