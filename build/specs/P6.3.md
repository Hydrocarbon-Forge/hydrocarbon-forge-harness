## Objective

Implement the comprehensive benchmark evaluation harness, task specification suite, comparison arms A–D, report generator, CLI subcommand, and standalone runner script per §13:
1. Task definition format and suite (`bench/tasks/**`):
   - Structured YAML frontmatter task specifications in Markdown defining task id, title, task class, tags, target repository fixture, setup commands, acceptance verification commands, and budget caps.
   - Benchmark task suite containing 6–10 representative coding tasks drawn from nominated repositories and fixtures, spanning classes: `feature`, `debug`, `refactor`, `mechanical`, `boilerplate`, and `tests`.
2. Benchmark evaluation arms (§13):
   - Arm A: Solo top-tier model session (`--mode solo --model <top>`, e.g., `claude-opus-5-5` or configured top tier).
   - Arm B: Solo cheap-tier model session (`--mode solo --model <cheap>`, e.g., `claude-haiku-5-5` or configured cheap tier).
   - Arm C: Substrate plan mode (`--mode plan`) with default multi-agent routing.
   - Arm D: Substrate plan mode with local-model workers (`--mode plan`) overriding `mechanical` and `boilerplate` tasks to local-model workers (OpenCode + llama.cpp).
   - Uniform budget caps and 3 repetitions per arm per task where affordable.
3. Observability, metrics collection, and report generation (`bench/report.ts`):
   - Telemetry collection per attempt: pass/fail verdict from external verify commands, first-pass verify rate (pass without heal/replan), total USD cost via usage ledger, wall-clock duration, token consumption, and failure classifications.
   - Comparative tabular summary across Arms A–D.
   - Empirical evaluation of hypotheses H1, H2, and H3 per §13:
     - H1: Arm C matches Arm A's pass rate on $\ge 70\%$ of tasks at lower cost.
     - H2: Substrate's first-pass verify rate beats Arm B.
     - H3: Arm D's pass rate on mechanical/boilerplate is within 10 percentage points of Arm C at near-zero marginal cost.
   - Exporters for Markdown reports, JSON data summaries, and formatted console tables.
4. CLI Subcommand and script entrypoint (`src/cli/bench.ts`, `scripts/bench.mjs`):
   - `substrate bench [options]` subcommand self-registering with `src/cli/registry.ts`.
   - Standalone executable runner script `scripts/bench.mjs` replacing the scaffold stub.
   - Execution flags: `--tasks`, `--arms`, `--repetitions`, `--max-budget`, `--top-model`, `--cheap-model`, `--local-model`, `--format`, `--output`, `--concurrency`, `--dry-run`.
5. Unit test suite (`test/unit/bench/**`):
   - Unit tests for task loading, arm configuration, runner loop, budget enforcement, hypothesis math, and reporting.

## Behavior

The benchmark subsystem executes according to the following decision trees:

1. Task loading and fixture validation:
   - For each candidate task spec path loaded from `bench/tasks/**` or `--tasks` glob:
     - IF task file lacks YAML frontmatter or required fields (`id`, `title`, `task_class`, `repo_fixture`, `verify`):
       - THEN throw validation error detailing missing or malformed fields.
     - ELSE IF `repo_fixture` directory or git reference does not exist:
       - THEN throw error `Fixture path not found: <repo_fixture>`.
     - ELSE IF `verify` command array is empty:
       - THEN throw error `Task must specify at least one verification command`.
     - ELSE:
       - Parse frontmatter into `BenchmarkTaskSpec` and append to active task suite.

2. Benchmark arm configuration resolution:
   - Given target arm $X \in \{\text{"A"}, \text{"B"}, \text{"C"}, \text{"D"}\}$:
     - IF $X === \text{"A"}$ (Solo top-tier):
       - THEN set `mode = "solo"`, `model = config.topModel ?? settings.roles.planner.model`, `effort = "high"`.
     - ELSE IF $X === \text{"B"}$ (Solo cheap-tier):
       - THEN set `mode = "solo"`, `model = config.cheapModel ?? settings.routing.mechanical.model`, `effort = "low"`.
     - ELSE IF $X === \text{"C"}$ (Substrate default plan):
       - THEN set `mode = "plan"`, utilizing default multi-agent routing table from settings.
     - ELSE IF $X === \text{"D"}$ (Substrate local-model workers):
       - THEN set `mode = "plan"`, overriding routing for `mechanical` and `boilerplate` task classes to local model (backend `opencode` with local llama.cpp provider), while preserving default routes for other task classes.

3. Suite execution and repetition runner:
   - IF `config.dryRun` is true:
     - THEN validate all task specifications and fixture repositories, display planned matrix of attempts (tasks $\times$ arms $\times$ repetitions), and exit 0 without invoking LLM backends.
   - ELSE:
     - Initialize worker concurrency pool with limit (default 2–3 per U13).
     - For each task in suite:
       - For each arm in selected arms:
         - For repetition $r \in [1 \ldots \text{repetitions}]$:
           - Initialize isolated throwaway git worktree or temporary directory from `repo_fixture`.
           - IF `setup` commands defined on task:
             - THEN execute setup commands in workspace; IF any setup command fails, THEN record attempt failure with error `setup_failed` and abort attempt.
           - Apply uniform budget caps (`budgetCapUsd`, `timeout_s`) to run options.
           - Execute task via Engine (`Engine.run`) or solo session.
           - Record usage ledger metrics (USD cost, tokens, duration).
           - Execute external acceptance `verify` commands in workspace:
             - IF all verify commands exit 0:
               - THEN set `passed = true`.
               - IF attempt reached pass on generation 1 attempt 1 without L0 heal or L1 replan:
                 - THEN set `firstPassVerified = true`.
                 - ELSE set `firstPassVerified = false`.
             - ELSE:
               - THEN set `passed = false` and `firstPassVerified = false`.
           - Remove isolated worktree and clean up temporary resources.

4. Hypothesis evaluation logic (§13):
   - H1 Evaluation (Arm C matches Arm A's pass rate on $\ge 70\%$ of tasks at lower cost):
     - For each task $T$, calculate $pass\_rate(C, T)$ and $pass\_rate(A, T)$.
     - IF $pass\_rate(C, T) \ge pass\_rate(A, T)$:
       - THEN record task $T$ as matched.
       - ELSE record task $T$ as unmatched.
     - Calculate $match\_fraction = matched\_count / total\_tasks$.
     - IF $match\_fraction \ge 0.70$ AND $total\_cost(C) < total\_cost(A)$:
       - THEN set `h1.supported = true`, evidence string noting match percentage and cost savings.
       - ELSE set `h1.supported = false`, evidence string noting failing condition.
   - H2 Evaluation (Substrate first-pass verify rate beats Arm B):
     - Calculate aggregate $first\_pass\_rate(C) = first\_pass\_verified(C) / total\_attempts(C)$ and $first\_pass\_rate(B) = first\_pass\_verified(B) / total\_attempts(B)$.
     - IF $first\_pass\_rate(C) > first\_pass\_rate(B)$:
       - THEN set `h2.supported = true`, evidence string showing rate delta.
       - ELSE set `h2.supported = false`, evidence string showing rate delta.
   - H3 Evaluation (Arm D pass rate on mechanical/boilerplate within 10 points of Arm C at near-zero marginal cost):
     - Identify subset of tasks with `task_class` in `["mechanical", "boilerplate"]`.
     - IF mechanical/boilerplate task count is 0:
       - THEN set `h3.supported = false` with evidence `not_applicable_no_mechanical_tasks`.
       - ELSE:
         - Calculate $mech\_pass\_rate(C)$ and $mech\_pass\_rate(D)$.
         - Calculate $mech\_cost(C)$ and $mech\_cost(D)$.
         - IF $(mech\_pass\_rate(C) - mech\_pass\_rate(D)) \le 0.10$ AND $(mech\_cost(D) \le 0.10 \times mech\_cost(C) \text{ OR } mech\_cost(D) \le 0.01)$:
           - THEN set `h3.supported = true`, evidence string detailing pass rate delta and cost savings.
           - ELSE set `h3.supported = false`, evidence string detailing failing condition.

5. CLI Subcommand handling (`substrate bench`):
   - Parse CLI arguments via `parseArgs`.
   - IF arguments contain unknown flags or invalid options (e.g., negative repetitions or unknown arm identifier):
     - THEN write error message to stderr and return exit code 2.
   - ELSE:
     - Invoke benchmark harness via `runBenchmarkSuite(config)`.
     - IF benchmark completes successfully:
       - THEN format report in requested format (`text`, `json`, or `markdown`), output to stdout or `--output` file, and return exit code 0.
       - ELSE IF fatal runtime error occurs:
         - THEN write error stack to stderr and return exit code 1.

## Invariants

- I2 (Workers never grade themselves): All benchmark pass/fail verdicts are strictly determined by external execution of deterministic acceptance `verify` commands; LLM self-reports are never trusted.
- I5 (Models are explicit): Model identifiers for Arms A, B, C, and D are explicitly declared or supplied via CLI flags; implicit model fallback is prohibited.
- I7 (Hard budgets everywhere): Identical budget caps (USD and timeout) are enforced uniformly across all arms for any given task attempt.
- Workspace isolation: Every attempt executes in an independent, temporary git worktree or fresh clone; filesystem changes never bleed across repetitions or arms.
- Uniform evaluation baseline: All arms evaluate against the identical codebase state, task prompt, environment configuration, and verification commands.
- Objective hypothesis derivation: Hypotheses H1, H2, and H3 are evaluated strictly via deterministic mathematical formulas over collected telemetry, never hardcoded.
- Concurrency bound: Worker concurrency respects configured pool bounds (default 2–3 per U13) to protect against provider rate limiting.

## Edge cases

- Task verify timeout: An acceptance verify command runs longer than `timeout_s`; process supervisor kills the process group with SIGKILL, marks the attempt failed, and logs `timeout`.
- Rate limit encountered: Backend returns HTTP 429 during a benchmark run; runner triggers exponential backoff or records rate-limited attempt without crashing the test battery.
- Local model offline for Arm D: llama.cpp server is unreachable or down; Arm D attempts record connection failure with diagnostic while Arms A, B, and C proceed unhindered.
- Single repetition requested: When `--repetitions 1` is passed, harness executes a single pass per task/arm; statistical averages handle single-sample counts cleanly.
- Zero pass rate on an arm: When all attempts fail for an arm, pass rate evaluates to 0.0% without division-by-zero errors.
- Zero cost across arms: In mock or free local-model runs where costs are $0.00, cost comparison evaluates strictly (`cost(C) < cost(A)` returns false if equal).
- Absence of mechanical tasks: If the nominated suite contains no `mechanical` or `boilerplate` tasks, H3 records status `not_applicable` rather than throwing an exception.
- Missing fixture repository: Preflight validation detects missing target directories before spawning worker processes, avoiding wasted spend.

## Guardrails

- Cost guardrail: Benchmark runs enforce an explicit per-attempt budget cap (default $2.00 or `--max-budget`); exceeding budget terminates execution immediately.
- Repository safety: Benchmark runs MUST NEVER mutate the root Substrate repository or uncommitted developer files; all work runs in isolated temporary worktrees.
- File boundary restriction: P6.3 writes files ONLY in `bench/**`, `src/cli/bench.ts`, `scripts/bench.mjs`, and `test/unit/bench/**`.
- Protected contracts: Files in `src/contracts/**` and `src/util/**` are protected and MUST NOT be edited.
- Credential safety: API keys, tokens, and authorization headers MUST NEVER be printed in benchmark reports, console output, or exported summaries.
