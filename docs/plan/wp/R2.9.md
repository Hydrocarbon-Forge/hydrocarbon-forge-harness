## Objective
Make the plan / work / fast model triple per provider (DECISIONS A3) drive routing. A run names a planner provider and a worker provider. Each task class maps to a profile slot. The escalation chain is derived from the worker provider's slots. Explicit `routing.<class>` entries still win, and the hard-coded model fallback in the router is removed.

## Interface
- `src/contracts/index.ts` adds:
  - `ProfileSlot = z.object({model: z.string(), effort: Effort.optional()}).strict()`
  - `Profile = z.object({plan: ProfileSlot, work: ProfileSlot, fast: ProfileSlot.optional()}).strict()`
  - `Settings.profiles` = optional `z.record(z.string(), Profile)`, keyed by provider name (`claude`, `opencode`, `agy`)
  - `Settings.defaults` = optional `z.object({planner_provider: z.string().optional(), worker_provider: z.string().optional()}).strict()`
- `src/config/index.ts`: export `validateProfiles(settings: Settings): void`. `loadSettings` calls it after `Settings.parse`. It throws `Error` with the message `profiles.<p> is required because defaults.<field> is "<p>"` when a default names a provider with no profile. The CLI already maps a `loadSettings` failure to exit 2.
- `src/roles/router.ts` exports:
  - `TASK_CLASSES = ["search","mechanical","boilerplate","tests","feature","refactor","debug","review"] as const`
  - `slotForClass(cls: string): "fast" | "work" | "plan"`: `search`, `mechanical`, `boilerplate` give `fast`; `tests`, `feature`, `refactor` give `work`; `debug`, `review` give `plan`; any other class gives `work`.
  - `resolvePlannerRoute(settings: Settings): Route`
  - `resolveTaskRoute(taskClass: string, generation: number, settings: Settings): Route` (signature unchanged, behaviour changed)
  - `escalationChain(settings: Settings): string[]`
- `src/engine/ladder.ts`: `evaluateEscalation(state, taskId, failure, settings, taskClass: TaskClass = "feature")`. The L1 route is `resolveTaskRoute(taskClass, nextGeneration, settings)`.

## Behavior
1. Route precedence for a task: (a) `settings.routing[class]` when it is a Route object; (b) when `defaults.worker_provider` is set, the slot `slotForClass(class)` of `profiles[worker_provider]`, using `fast` and falling back to `work` when `fast` is absent; (c) `settings.routing.feature` when it is a Route object. Otherwise throw `Error("no route configured for class '<cls>': set routing.<cls> or profiles plus defaults.worker_provider")`. The hard-coded `claude-sonnet-5-5` fallback is deleted.
2. Generation 1 uses that route. Generation g > 1 moves along `escalationChain(settings)`: find the index of the base route's model, add g-1, and clamp to the last index. When the base model is not in the chain, use index g-1 clamped.
3. `escalationChain` = unique model ids of `[fast?.model, work.model, plan.model]` of the worker provider, in that order, repeats removed. When no profile is set, it is `settings.routing.escalation` if that is an array, else `[]`.
4. `resolvePlannerRoute`: when `defaults.planner_provider` is set, `{backend: <provider>, model: profiles[p].plan.model, effort: profiles[p].plan.effort}`. Otherwise `settings.roles.planner`. The planner never names a model in a prompt.
5. The worker and planner providers may differ. Nothing in this WP requires them to match.
6. `ladder.ts` L1 no longer reads `routing.feature` or the literal `claude-sonnet-5-5`.
7. `src/spec/rules.ts` rule L015 (class must be configured) treats a class as configured when `routing[class]` exists or `defaults.worker_provider` is set with that class's slot present.
8. Explicit `routing.<class>` entries still validate exactly as before.

## Invariants
- The routing functions are pure: same settings and inputs give the same Route.
- No model id literal is added to `src/`.
- `routing.escalation` stays valid as the legacy chain when no profile is configured.

## Edge cases
- A profile with no `fast` slot: `search` routes to the `work` model.
- `fast` and `work` name the same model: the chain has two entries, not three.
- `defaults.planner_provider` set, `profiles` missing that provider: `loadSettings` throws the validation error in Interface.
- Generation past the end of the chain stays on the last model.
- A class not in `TASK_CLASSES` routes to `work`, never throws.

## Guardrails
- No security hardening beyond the plan (DECISIONS A6): no new sandbox, environment scrubbing or permission-file checks.
- Never write a raw IP address or port in code, specs, docs or fixtures.
- Not done if the routing is reachable only from tests. The E2E in Done when must run the built CLI with a profile in settings.
- No hard-coded model ids in `src/roles/router.ts` or `src/engine/ladder.ts`.
- Do not change the governor step of `routeRequest` in `router.ts`. The governor is out of scope.
- No test-only branches in `src/`.
