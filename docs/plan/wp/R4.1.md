## Objective
Give agents one structured way to start a run: a JSON request file or stdin, validated before any work starts, with machine-readable errors. Flags such as `--plan` and `--work` build the same object. Nothing is accepted and then ignored.

## Interface
- `src/contracts/request.ts` exports `RunRequest` (zod, `.strict()`):
  - `goal: string` (non-empty after trim)
  - `planner?` and `worker?`: `{provider: "claude" | "opencode" | "agy", model?: string, effort?: Effort}`
  - `mode?: "auto" | "solo" | "plan"`
  - `verify?: string[]` (each non-empty)
  - `budget?`: `{max_usd?: number, max_tokens?: number, max_wall_min?: number}`
  - `permission_mode?: PermissionMode`
  - `context?: string[]` (repo-relative file paths)
- `src/cli/request.ts` exports `loadRequest(source: string, stdin: string | undefined, flags): RunRequestResult`, where the result is `{ok: true, request, overrides} | {ok: false, problems: Problem[]}` and `Problem = {field: string; message: string; fix: string}`.
- CLI: `--request <file|->`, `--plan <provider[:model[:effort]]>`, `--work <provider[:model[:effort]]>`. These are added to the dispatcher option table. `--plan` and `--work` set `planner` and `worker`.
- Invalid input prints one JSON object to stdout: `{"error":"invalid_request","problems":[{"field","message","fix"}]}` and exits 2, whatever `--output-format` is.

## Behavior
1. `--request <file>` reads JSON from the file. `--request -` reads stdin. Unparseable JSON is a problem with field `request` and the parser message.
2. Schema problems are reported per field (zod path), each with a `fix` line such as `remove the unknown key 'scope'`.
3. `scope` is rejected: `{field: "scope", message: "scope is not enforced in this version", fix: "remove scope"}`. No accepted field may lack an effect.
4. `context[i]` must exist under the repo root; otherwise problem `context[i]`. Valid entries are appended to the planner's `instruction_files` list (R3.1).
5. Provider resolution: `planner` = `request.planner` (or `--plan`) else `defaults.planner_provider`. `worker` likewise with `defaults.worker_provider`. Mode `solo` needs only the worker. Missing provider: problem `planner.provider` (or `worker.provider`) with fix `pass --plan <provider> or set defaults.planner_provider`.
6. Model: an explicit `model` wins over the profile slot. With no model and no slot, problem `<role>.model`. For an installed provider, a model not in `listModels()` (through the R2.7 catalog) is problem `<role>.model` with message `unknown model '<id>'` and fix `valid ids: <comma list>`. For a provider that is not installed the model check is skipped.
7. Effort, when given, must be in `Effort`; otherwise problem `<role>.effort`.
8. Conflicts: a positional prompt together with `--request` is problem `goal` ("both a prompt and a request file were given"). `--mode solo` with `--plan` is problem `planner` ("solo mode runs no planner"). Flags override the same field from the file.
9. The valid request maps to `RunOptions`: `prompt = goal`, `mode`, `permission_mode`, `overrides.roles.planner`, `overrides.roles.worker`, `overrides.budgets`, and `verify` into `overrides.verify`. The `context` list goes to the planner through `overrides.context`.
10. `run` and `plan` take the request path before any other work. Exit code is 2 on any problem, 0 or the run's code otherwise.

## Invariants
- Validation has no side effects: no file is written and no run directory is created when a problem exists.
- Problems are sorted by field, then by the order found, so output is deterministic.
- The request schema is the single source. Flags never bypass it.

## Edge cases
- Empty `goal` after trim: problem `goal`.
- `--request` file not found: problem `request` with message `file not found: <path>`.
- Unknown model with an uninstalled provider: accepted (cannot verify); the run's own adapter check reports it later.
- Both `--request -` and stdin prompt: the file wins; no prompt is read twice.

## Guardrails
- No security hardening beyond the plan (DECISIONS A6): no new sandbox, environment scrubbing or permission-file checks.
- Never write a raw IP address or port in code, specs, docs or fixtures.
- Not done if the request is reachable only from unit tests. The E2E must run `run --request <file>` through the built CLI.
- No stub validation. Every field in the schema is either used or rejected.
- Do not change the model catalog (R2.7) or routing (R2.9).
- No test-only branches in `src/`.
