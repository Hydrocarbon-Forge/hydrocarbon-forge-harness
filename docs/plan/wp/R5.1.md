## Objective
Give an agent such as Hermes one short document that tells it how to use Substrate end to end: list models, choose providers, build a request, run, handle `needs_input`, and read usage. Every command the guide shows is executed by a test, so the guide cannot drift from the CLI.

## Interface
- `assets/prompts/caller/substrate-caller.md` is the guide. It is a prompt asset, loaded by nothing in `src/` in this WP.
- `docs/reference/caller-guide.md` is a byte-identical copy of the asset.
- `test/e2e/caller-guide.test.ts` holds a table of `{command, expectedExit}` rows. It runs each through `runSubstrate` (from `test/e2e/helpers/run-substrate.ts`).

## Behavior
1. The guide has these sections in order: `## Before you start` (install check with `substrate doctor --output-format json`), `## Choose models` (`substrate models --output-format json`), `## Build a request` (the JSON fields of `RunRequest` with one complete example), `## Run` (`substrate run --request -` reading the request from stdin, with `--output-format json`), `## Handle needs_input` (exit 3, `substrate resume <run_id> --answers -`), `## Read usage` (`substrate usage --by model --output-format json`), `## Exit codes` (0, 1, 2, 3, 4, 130, 143 with one meaning each, from SUBSTRATE-PLAN 4.6).
2. Every command in the guide is written as a line starting with `substrate ` inside a fenced block.
3. The test table contains each such line, with the fake executables and a scenario that makes it succeed. Expected exits: `doctor` 0, `models` 0, `run --request -` 0, `resume --answers -` 0 (after a `needs_input` run), `usage` 0.
4. A second test reads the guide, extracts every `substrate ` line, and asserts each appears in the table. A new command in the guide without a row fails the test.
5. A third test asserts the two guide copies are byte-identical.

## Invariants
- The guide never names a model id that is not supplied by `models --output-format json`.
- The guide never mentions the governor, the TUI or hooks.
- Exit codes in the guide match SUBSTRATE-PLAN 4.6.

## Edge cases
- A command in the guide that needs a prior run (`resume`): the test runs the `needs_input` scenario first in the same temp repository.
- The request sent on stdin is a valid `RunRequest` with `mode: "solo"`.

## Guardrails
- No security hardening beyond the plan (DECISIONS A6): no new sandbox, environment scrubbing or permission-file checks.
- Never write a raw IP address or port in code, specs, docs or fixtures.
- Not done if the guide is only written, not tested. The test must run every command through the built CLI.
- No placeholder model ids in the guide. Use the wording "an id from `models`".
- No prompt text in TypeScript; the guide lives in `assets/` and `docs/` only.

## Out of scope
A loader for the guide in `src/` (not required). MCP. Any governor or agent-to-agent protocol.
