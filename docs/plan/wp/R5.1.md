## Objective
Two things, in this order. (1) The documentation describes only what the code does, and `docs:check` fails when a documented flag, command, environment variable or settings key has no implementation. (2) An agent such as Hermes gets one short guide that tells it how to use Substrate end to end (list models, choose providers, build a request, run, handle `needs_input`, read usage), and a test executes every command the guide shows so the guide cannot drift from the CLI. Superseded sections of SUBSTRATE-PLAN.md are marked as superseded by DECISIONS.md.

## Interface
- `scripts/docs-check.mjs` gains four rules, each printed as `RULE path:line message`, in the same style as the R0.1 scripts. Exit 0 clean, 1 violations, 2 internal error.
  - `DOC-FLAG`: a `--flag` token in `README.md` or `docs/reference/*.md` must appear in `src/cli/dispatcher.ts` (`CLI_OPTIONS` keys) or in another file under `src/cli/`.
  - `DOC-CMD`: a `substrate <word>` token in those files must be a registered command name or alias (names parsed from `name:` and `aliases:` in `src/cli/commands/*.ts`).
  - `DOC-ENV`: a `SUBSTRATE_[A-Z_]+` token must appear as a literal in some file under `src/`.
  - `DOC-KEY`: a dotted settings key in the table of `docs/reference/config.md` must have its last segment read as a property (`.<leaf>`, `?.<leaf>` or `["<leaf>"]`) in a file under `src/` other than `src/contracts/**`, `src/config/**` and `src/cli/commands/config.ts`.
- Marker for superseded sections: a block quote line beginning `> **Superseded by DECISIONS.md**` directly under the section heading.
- `assets/prompts/caller/substrate-caller.md` is the guide (a prompt asset, loaded by nothing in `src/`). `docs/reference/caller-guide.md` is a byte-identical copy.
- `test/e2e/caller-guide.test.ts` holds a table of `{command, expectedExit}` rows and runs each through `runSubstrate` (from `test/e2e/helpers/run-substrate.ts`).

## Behavior
1. Each documented flag, command, variable and key is checked as above, and each failure prints one line. The output lists the number of checks per rule, then `OK` or `FAIL: <n> violation(s)`.
2. `README.md` and the reference files describe: the CLI commands that exist (R1 to R4); the configuration layers in the order R1.6 implemented; the adapters with their pins. They contain no TUI claims, no hooks as available features, no governor as a default path, and no `-w/--worktree` flag (R1.8 removed it). Remove the "under remediation" banner at the top of `README.md`.
3. `docs/reference/local-model.md` (created by R4.3) and `caller-guide.md` are kept and checked by the same rules.
4. In `SUBSTRATE-PLAN.md`, each section that DECISIONS.md supersedes gets the marker from Interface. Sections not superseded are not edited.
5. `test/fixtures/docs-check/bad/README.md` contains one violation of each rule. `clean/README.md` contains none. The unit test runs the script with `--root` on each and asserts the output.
6. The caller guide has these sections in order: `## Before you start` (`substrate doctor --output-format json`), `## Choose models` (`substrate models --output-format json`), `## Build a request` (the JSON fields of `RunRequest` with one complete example), `## Run` (`substrate run --request -` reading the request from stdin, with `--output-format json`), `## Handle needs_input` (exit 3, `substrate resume <run_id> --answers -`), `## Read usage` (`substrate usage --by model --output-format json`), `## Exit codes` (0, 1, 2, 3, 4, 130, 143 with one meaning each, copied from SUBSTRATE-PLAN 4.6).
7. Every command in the guide is a line starting with `substrate ` inside a fenced block. The e2e test table contains each such line, with the fake executables and a scenario that makes it succeed (expected exits: `doctor` 0, `models` 0, `run --request -` 0, `resume --answers -` 0 after a `needs_input` run, `usage` 0). A second test extracts every `substrate ` line from the guide and asserts each appears in the table. A third asserts the two guide copies are byte-identical (create the copy with `cp assets/prompts/caller/substrate-caller.md docs/reference/caller-guide.md`).

## Invariants
- The docs-check script reads files only, its output is deterministic (sorted by file, then line), and its rules check existence in code, not correctness of behaviour.
- The guide never names a model id that `models --output-format json` does not supply, never mentions the governor, the TUI or hooks, and its exit codes match SUBSTRATE-PLAN 4.6.

## Edge cases
- A flag written as `--model=<id>` in docs: the part before `=` is checked.
- A `substrate` token inside a code span that is a path, such as `substrate/runs/`: not a command (the token must be followed by a space or the end of the span).
- A settings key with a `*` segment: skipped, as in R0.1.
- A guide command that needs a prior run (`resume`): the test runs the `needs_input` scenario first in the same temp repository. The request sent on stdin is a valid `RunRequest` with `mode: "solo"`.

## Guardrails
- No security hardening beyond the plan (DECISIONS A6): no new sandbox, environment scrubbing or permission-file checks.
- Never write a raw IP address or port in code, specs, docs or fixtures.
- Not done if the checks are only unit-tested: `npm run docs:check` must pass on the real repository, and the guide must be tested through the built CLI.
- Do not weaken a rule to make the docs pass. Fix the document, or record the violation in the debt allowlist only with `until` set to a real WP id.
- No placeholder model ids in the guide; use the wording "an id from `models`". No prompt text in TypeScript.

## Out of scope
Symbol-level checks (R0.6). Archive docs. Benchmark and packaging docs. Any change to `src/`. A loader for the guide in `src/`. MCP.
