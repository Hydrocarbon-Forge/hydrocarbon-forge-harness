## Objective
The first retry is informed by the real failure, and every limit is enforced. A failing verify resumes the same worker session in the same worktree with the real failing output. Per-task budgets and timeouts end only the task. Run budgets pause the run. Rate limits come from typed events, back off, and halve concurrency on a per-run copy.

## Interface
- L0 heal is `runWorker`'s second attempt (src/roles/worker.ts) and the `heal` action type in `src/engine/actions/task.ts`. It spawns with `session: {resume: <session_id from attempt 1>}`, `cwd` = the same worktree, and prompt `render(loadTemplate("worker/heal.md"), {failures})`.
- `failures`: built in code. For each failing VerifyResult: `Command: <cmd>`, `Exit code: <n>`, then `Stdout:` and `Stderr:` tails. Capped at 8192 bytes with `capBytes`.
- `task.healing` data gains `failures: string` (the rendered text). `rate_limit.backoff {task_id, concurrency}` is added to the catalog in `src/contracts/events.ts`.
- `EffectContext` (src/engine/effects.ts) gains `concurrency: number`, initialised from `settings.concurrency.workers` and halved on rate limit with floor 1. `nextActions(state, settings, {concurrency})` takes the effective limit as an optional third argument.
- `evaluateEscalation` is unchanged in signature. Its `permission_denied` and `rate_limited` branches stay.

## Behavior
1. Heal happens only for `verify_failed` on attempt 1 of a generation. It is skipped after a budget, timeout, scope or protected failure.
2. The heal prompt is rendered from the real failing VerifyResults of attempt 1. The hard-coded heal strings in `src/roles/worker.ts` and `src/engine/effects.ts` are deleted.
3. The heal session resumes the stored session id. The worktree is never recreated.
4. Per-task budget: totals of cost, input plus output tokens, and assistant turns are kept per generation, across attempt 1 and heal. Turns count `assistant.text` events. Crossing `max_usd`, `max_tokens` or `max_turns` calls `handle.kill("budget")` and fails the task with `budget_exceeded`. The run is not paused.
5. Timeout: `timeout_min` (spec, then settings, then 30) becomes `timeout_ms` with no upper cap (the `< 3600000` guard is deleted). The timer is armed for every attempt, calls `kill("timeout")`, and fails the task with `timeout`.
6. Run budget: after each `usage.recorded`, the total is `state.usage.total_usd` plus the pending cost. At 80 percent, emit `run.budget.warning` once. At 100 percent, emit `run.budget.exceeded` and `run.paused {reason: "budget_exhausted"}`, and kill the session. `budgets.run.max_tokens` is enforced the same way.
7. Rate limit: a typed `error` event with `kind: "rate_limit"` (never string matching) kills the session with `"cancel"` and backs off for 1000 ms, then 2000 ms, then 4000 ms, retrying the same attempt. The attempt number is not consumed. On the fourth rate limit for the task, the task fails with `rate_limited`, the concurrency is halved (floor 1) on `EffectContext`, and the L3 rule pauses with `rate_limited` (exit 3).
8. The concurrency halving never mutates `settings`. A `rate_limit.backoff` event records the new value.
9. Permission denial (`permission.denied` or `SessionResult.denials`) pauses with `permission_denied`, unchanged.
10. A session killed for `budget` or `timeout` is never retried by heal.

## Invariants
- No budget check is performed on a copy that discards usage.
- The run total used for the 80 percent and 100 percent checks never double counts an event (R1.4 owns the reducer; this WP reads `state.usage` only).
- The heal prompt in the event log contains the real failing command output.

## Edge cases
- Heal session missing (no session id reported): the attempt fails `worker_crashed`, no heal.
- Usage event arrives after a budget kill: ignored after the kill.
- A task timeout at 60 minutes or more: fires (the cap is removed).
- Rate limit on the heal attempt: same backoff, counted within the same task.

## Guardrails
- No security hardening beyond the plan (DECISIONS A6): no new sandbox, environment scrubbing or permission-file checks.
- Never write a raw IP address or port in code, specs, docs or fixtures.
- Not done if the budgets and rate limits are reachable only from tests. The E2E must run the built CLI with fake harness scenarios for overshoot, hang and rate limit.
- No string matching on error messages. No `Rate limit` checks.
- Do not mutate `ctx.settings` or any shared object.
- No prompt text in TypeScript. No stub or placeholder bodies. No test-only branches in `src/`.

## Out of scope
Escalation L1 to L3 and failure packets (R3.5). Integration (R3.6). Solo mode (R3.8). Pricing (R2.1).
