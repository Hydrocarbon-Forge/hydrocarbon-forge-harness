## Objective
Failures replan for real. L1 gives the planner the complete failure packet and writes back a revised task spec that is actually used by the next generation. L2 amends contracts and invalidates only the dependents that have not merged. L3 pauses the run for a human. Nothing is replanned by a hard-coded prompt.

## Interface
- `evaluateEscalation(state, taskId, failure, settings, taskClass: TaskClass = "feature")` (src/engine/ladder.ts). L1 route = `resolveTaskRoute(taskClass, nextGeneration, settings)` (R2.9).
- `executeReplan(opts)` (src/engine/replan.ts) is the only L1 and L2 path. It is called by the `replan` action (`src/engine/actions/replan.ts`).
- `buildFailurePacket` (src/engine/packet.ts) returns a complete `FailurePacket`. Its `attempts` are the WorkerReports read from `<runDir>/packets/<task>-g<n>-attempt<k>.json`, which the worker action writes.
- Prompts: `render(loadTemplate("planner/replan-l1.md"), vars)` and `replan-l2.md`. System = `agents/planner.md` body + `prompts/planner/format.md` (README table). The hard-coded text in `src/roles/prompts/replan.ts` is removed.
- `reducer.ts`: `EngineState` gains `l2_count: number` and `l2_done: boolean` (replacing the `(state as any)` fields). `tasks.invalidated {task_ids}` sets those tasks to PENDING.

## Behavior
1. Escalation order for a failed task: `permission_denied` and `rate_limited` go to L3. `verify_failed` on attempt 1 goes to L0 (R3.4). Any other failure goes to L1 while `generation <= budgets.l1_replans_per_task` (default 2, so the highest generation is 3). After that, L2 while `l2_count < budgets.l2_per_run`. Otherwise L3 with `needs_human`.
2. L1 packet: `attempts` from the packet files, `diff` = `generateDiff` of the failed worktree against the run branch, written to `<runDir>/packets/<task>-g<n>.patch` with `patch_path` set. `verify_output` = the last attempt's VerifyResults. `scope_violations`, `worker_summary` (last `final_message`, capped at 2048 bytes) come from the worker. `related_contracts` = the task's `read` entries that appear in `manifest.contracts.files`. `dependents` = every task that transitively depends on this one.
3. L1 emits `replan.started {task_id, generation: next, target_tier: model}`, spawns the planner with the L1 prompt and the route from rule 1, and collects `<runDir>/tasks/<task>.md`.
4. L1 accepted only when the final line is exactly `REVISED <TASK_ID>` for this task and the file parses with `parseTaskSpec` and passes `lintPlan` in the context of the current plan. Then the revised spec replaces the task's spec for the next generation and emits `task.replanned` and `replan.finished`. The next generation gets a fresh worktree and emits `task.ready`.
5. L1 finish `ESCALATE: <reason>`, a missing or invalid spec, or any other final line is treated as an escalation to L2 (rule 6). It is recorded with the reason in `replan.started`.
6. L2 is taken when the cap allows it. It increments `l2_count`, sets `l2_done`, emits `replan.l2`, and spawns the planner with `replan-l2.md`. Its final line must be `AMENDED`. The amended manifest is re-linted with `lintPlan`, the contracts are typechecked, and `commitContractStubs` commits them (R3.1 rules).
7. After a valid L2, only the dependents of the failed task that are not MERGED are invalidated (`tasks.invalidated {task_ids}`). Merged tasks are never touched. The failed task moves to the next generation and emits `task.ready` when its dependencies are MERGED.
8. L2 whose final line is `NEEDS INPUT` (with `QUESTIONS.md`) or any invalid output pauses with `needs_human` (exit 3).
9. L3 pauses with the reason in the escalation (`run.paused`).
10. The per-task timeout and budget failures trigger L1. The run budget never triggers replanning (R3.4).
11. Each planner usage event emits `usage.recorded {role: "planner"}`.

## Invariants
- Every replanned task gets a new generation. The generation is never reused.
- A merged task is never invalidated, re-run or re-linted by L2.
- The planner's writes outside `tasks/<id>.md` and the amended manifest are ignored by the engine.
- The packet written to disk validates against `FailurePacket`.

## Edge cases
- Packet build fails (e.g. no worktree): the packet is still written, with empty diff stat and the patch path set to an empty file. Nothing is fabricated: `attempts` and `verify_output` are whatever was recorded.
- Revised spec drops a required heading: rule 5 (L2).
- Two tasks fail in the same batch: each gets its own packet and its own L1 spawn, in task id order.

## Guardrails
- No security hardening beyond the plan (DECISIONS A6): no new sandbox, environment scrubbing or permission-file checks.
- Never write a raw IP address or port in code, specs, docs or fixtures.
- Not done if replanning is reachable only from tests. The E2E must drive the built CLI with the fake planner scenario.
- No hard-coded replan prompt text in TypeScript. No placeholder revised specs. No edit of files other than the revised spec and the amended manifest.
- Do not delete the packet files.
- No test-only branches in `src/`.

## Out of scope
Question answers and resume (R4.2). Charter and history in the planner prompt (R4.5). The governor.
