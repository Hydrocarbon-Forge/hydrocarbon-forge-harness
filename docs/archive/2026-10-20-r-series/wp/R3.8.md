## Objective
`substrate run --mode solo` runs one worker in its own worktree, with no planner and no manifest, verified by the same code path as plan mode. Solo never fabricates a file, never runs `git add -A`, and never reports a pass without verify commands or a warning that none exist.

## Interface
- `substrate run --mode solo [--verify "<cmd>"]...` where `--verify` is repeatable. It is added to the dispatcher's option table (src/cli/dispatcher.ts) as a multiple string option and to `ParsedCliFlags` as `verify: string[]`.
- Solo task id is `SOLO` (uppercase; `solo` fails `TaskId`).
- `src/engine/actions/route.ts` solo branch emits `run.routed {mode: "solo"}`, `setup.done {tasks: [{id: "SOLO", depends_on: [], write: ["**"], create: ["**"], protected: []}]}` and `task.ready {task_id: "SOLO"}`.
- `src/engine/actions/solo.ts` builds the solo spec in code: `id: "SOLO"`, `class: "feature"`, `title: "solo task"`, `write: ["**"]`, `create: []`, `read: []`, `protected: []`, `verify` = the verify list, budget from settings. It writes the goal text as `.substrate-task/TASK.md` through R3.3's worker path, and calls `runWorker`.
- `getDefaultVerify("other")` returns `[]` (the echo command is deleted).

## Behavior
1. Verify list: each `--verify` value becomes `{run: <value>, timeout_s: 300}`. With no `--verify`, `detectEcosystem(repoRoot)` then `getDefaultVerify`. An empty list prints `warning: no verify commands; only scope and budget checks apply` to stderr, and the run continues.
2. The worker is `runWorker` (R3.3) with `cwd` = `.substrate/worktrees/<run_id>/SOLO-g1/`. Its route is `resolveTaskRoute("feature", 1, settings)` (R2.9). Scope, protected, verify, commit and events are exactly the plan-mode worker path.
3. Heal (L0, R3.4) and budgets (R3.4) apply unchanged.
4. The solo commit is made by `commitAllowed` on the task branch (R3.3). The `git add -A` and direct `git commit` in the solo action are deleted, along with the `// solo edit` writes.
5. After pass, the task branch is merged into the run branch by the batch merge (R3.6). The run finishes with exit 0 through the integration action.
6. A solo run never writes `manifest.yaml` or `tasks/`, and never calls the planner.
7. The user's checkout is untouched (no merge unless `git.auto_merge` is true, handled by R3.7).
8. Smoke: in `test/e2e/smoke.test.ts`, remove the `it.fails` marker from the full-run test only. The `--help` test is handled by R1.1.

## Invariants
- No file content is written by the engine except the goal text in `TASK.md` and the worker's own edits.
- Solo tasks follow the same event sequence as plan tasks, with `task_id` = `SOLO`.
- With no verify commands, the run still requires scope and budget checks to pass.

## Edge cases
- `--verify` given twice: both run in order; the task passes only if all exit 0.
- Ecosystem `other` with no `--verify`: warning, then only scope and budget checks decide.
- Worker makes no change: verify decides; a pass with no commit is allowed.

## Guardrails
- No security hardening beyond the plan (DECISIONS A6): no new sandbox, environment scrubbing or permission-file checks.
- Never write a raw IP address or port in code, specs, docs or fixtures.
- Not done if solo mode is reachable only from tests. The E2E must run `run --mode solo` through `runSubstrate`.
- No hard-coded solo output, no `echo` verify, no `// solo edit` writes.
- No test-only branches in `src/`.
- The full plan-mode smoke test must pass after this WP. If it does not, do not remove its marker.

## Out of scope
Planner-driven runs (R3.1 to R3.5). Request files (R4.1). Solo-specific budgets. The governor.
