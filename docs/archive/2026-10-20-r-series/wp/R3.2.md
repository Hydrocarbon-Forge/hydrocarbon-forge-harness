## Objective
Tasks run in dependency order, resume continues the work that was in flight, and a run's final status and exit code come from its state. A run that stops with work left over must never report success.

## Interface
- `src/engine/scheduler.ts` exports `promoteReadyTasks(state: EngineState): TaskId[]` (tasks that become READY) and keeps `detectOverlap` and `scheduleNextTasks`. `scheduleNextTasks` gains no new parameter.
- `src/engine/reducer.ts`: `TaskRuntimeState` gains optional `depends_on?: TaskId[]`, `write?: string[]`, `create?: string[]`. `setup.done` data is `{tasks: [{id, depends_on, write, create}]}` and the reducer stores those fields.
- `src/engine/effects.ts` `nextActions(state, settings)` keeps its signature. `runEffectsLoop` keeps its signature.
- Settings: `concurrency.workers` is read with no fallback (`?? 4` is deleted).
- `src/engine/engine.ts`: `run` and `resume` use `EventStoreImpl` (src/store/event-store.ts) for every append and read.
- Adapter cap: a READY task whose route's backend has `adapter.capabilities.max_concurrency` set is not started while that many tasks on that backend are in flight.

## Behavior
1. `setup` (src/engine/actions/setup.ts) emits `setup.done` with the task list described above. It emits `task.ready` only for tasks whose `depends_on` is empty. `computeDagLayers` is used only to reject cycles.
2. After every reduced event, `runEffectsLoop` calls `promoteReadyTasks`. Each returned task gets a `task.ready` event. A PENDING task becomes READY only when every dependency is MERGED. Requiring MERGED matters: a dependent's worktree is created from the run branch, so it can only see a dependency's changes after that dependency has been merged.
3. A PENDING task with a dependency in BLOCKED or ABANDONED becomes BLOCKED through `task.blocked`.
4. `nextActions` emits `merge` for all PASSED tasks, in topological order then id, whenever at least one exists and no task is RUNNING, SCOPE_CHECK or VERIFYING. This keeps dependents moving. It no longer waits for every task to pass.
5. `nextActions` starts at most `concurrency.workers` tasks minus the in-flight count. A READY task is skipped while an in-flight task's `write` or `create` patterns overlap its own (`detectOverlap`). A READY task routed to a backend whose `capabilities.max_concurrency` is set is also skipped while that many in-flight tasks use the same backend.
6. When `runEffectsLoop` ends with no actions while the state is not FINISHED, FAILED, CANCELLED or PAUSED, it appends `run.finished {exit_code: 1, status: "failed", reason: "stalled"}`. The engine never reports `finished` unless the `integration` action emitted `run.finished` with exit 0.
7. Exit codes from state: FINISHED 0; FAILED 1; CANCELLED 1; PAUSED with `budget_exhausted` 4; PAUSED with `needs_human`, `needs_approval`, `permission_denied`, `rate_limited` or `backend_unavailable` 3; PAUSED with `user_cancel` 130. `run`, `plan` and `resume` return `summary.exit_code` directly. The three duplicate `mapSummaryExitCode` functions are deleted.
8. `resume <run>` replays `events.jsonl` through `reduce`. Tasks in RUNNING, SCOPE_CHECK or VERIFYING are moved back to READY with `task.ready {task_id, resumed: true}`. The next worker action resumes the stored `session_id` when one exists and its worktree exists, otherwise starts a new session. A HEALING task stays HEALING.
9. The `run.resumed` seq is `lastSeq + 1`, not `events.length + 1`.
10. The run lock is held for the whole `run` and `resume`. A live lock held by another pid makes the command exit 2 with `Error: run <id> is locked by pid <pid>`. A stale lock is taken over.

## Invariants
- Every state change comes from an appended event. `promoteReadyTasks` and `nextActions` are pure.
- A dependent never starts before every dependency is MERGED.
- `seq` is strictly increasing across `run`, `resume` and `promote` events.
- A PAUSED or terminal run is never reported as `finished`.

## Edge cases
- A task that fails with a replan pending is FAILED for scheduling but not BLOCKED for its dependents until the replan gives up.
- `resume` on a finished run prints `Run <id> is already finished. Nothing to resume.` and exits 0 (unchanged).
- A kill between `task.session.started` and `task.session.ended`: resume re-readies the task (rule 8).
- Torn last line in `events.jsonl`: skipped by `EventStoreImpl.readAll`.
