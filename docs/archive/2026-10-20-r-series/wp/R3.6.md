## Objective
Merging never touches the user's checkout. Each batch of passed tasks is merged inside a run-owned integration worktree, verified there, and only then becomes the run branch's new tip. A failing batch is bisected to its culprit deterministically, within a fixed bound. Every batch records a checkpoint that `undo` can return to.

## Interface
- `src/git/merger.ts` exports:
  - `createIntegrationWorktree(repoRoot, runId, baseSha): Promise<string>` returns `.substrate/worktrees/<run_id>/integration`, created detached at `baseSha` (or reused if it exists).
  - `mergeInto(worktreePath, taskBranch, msg): Promise<string>` runs `git merge --no-ff -m <msg> <taskBranch>` in that worktree and returns the new HEAD. It never checks out a branch in another worktree.
  - `advanceRunRef(repoRoot, runId, newSha, expectedOldSha): Promise<void>` runs `git update-ref refs/heads/substrate/runs/<id> <new> <old>`.
  - `verifyIn(worktreePath, commands, settings): Promise<boolean>` runs `VerifyRunner` with `cwd` = worktree, `sandbox` = `settings.sandbox.enabled`, `network` = `"allow"`.
- `TaskMerger.preflight` keeps its signature. Its `target` argument is the integration HEAD sha.
- `TaskMergerImpl.mergeTask` (which checked out branches in the user's checkout) and `rollbackCheckpoint` (which ran `git reset --hard` in that checkout) are removed. Rollback is `advanceRunRef` or a reset inside the integration worktree only.
- `src/engine/actions/merge.ts` exports the per-batch `merge` action. `src/engine/actions/integrate.ts` exports the final `integration` action.

## Behavior
1. `merge` (batch) takes the PASSED tasks in topological order, then task id. It creates or reuses the integration worktree at the current run-branch sha (`preBatchSha`).
2. For each task: `preflight(repoRoot, integrationHead, taskBranch)`. A conflict emits `merge.conflict {task_id, conflict_files}` and `task.failed {task_id, failure_class: "merge_conflict"}`. That task goes to L1 (R3.5). The batch stops.
3. Otherwise `mergeInto(integrationWorktree, taskBranch, "merge: task <id>")`.
4. After all tasks merge into the integration worktree, run `manifest.integration_verify` with `verifyIn`. Pass: `advanceRunRef(repoRoot, runId, integrationHead, preBatchSha)`, then emit `task.merged {task_id}` for each task and `batch.merged {batch, checkpoint_ref: preBatchSha}`.
5. Fail: bisect. Reset the integration worktree to `preBatchSha`. Merge the batch's tasks one at a time, verifying after each. The first failing task is the culprit. Emit `bisect.started`, then `bisect.culprit {culprit_task_id}`, then `task.failed {task_id: culprit, failure_class: "integration_failed"}`. Reset the integration worktree to the last good sha. Tasks not culprit remain PASSED and merge again later.
6. Bound: one `merge` action performs at most `1 + number of batch tasks` integration verify runs. Replan caps (R3.5) bound the rest.
7. `integration` (final, when every task is MERGED): verify the run branch in the integration worktree. Pass: `integration.finished {passed: true}`, `run.finished {exit_code: 0}`. Fail: `integration.failed {base: false}` and `run.finished {exit_code: 1, status: "failed"}`, with no bisect.
8. The base-ref check (currently `ctx.baseChecked`) stays: before the first batch, `manifest.integration_verify` runs on `manifest.base_ref` in a detached worktree. Failure emits `integration.failed {base: true}` and fails the run.
9. The user's checkout (`ctx.repoRoot`) receives no `checkout`, `reset`, `merge`, `rm` or `update-ref` from any path in this WP.

## Invariants
- `refs/heads/substrate/runs/<id>` moves only through `advanceRunRef` with an expected old value.
- A batch's `checkpoint_ref` is the run-branch sha before that batch.
- Untracked and modified files in the user's checkout are byte-identical before and after a run.

## Edge cases
- A task branch that no longer exists: `preflight` fails with a clear message and the task goes to L1.
- The integration worktree exists from a previous crash: reused, reset to the run-branch sha before the batch.
- `integration_verify` is empty: verify passes trivially and no command runs.
- Culprit is the only task in the batch: the batch becomes empty after the failure.

## Guardrails
- No security hardening beyond the plan (DECISIONS A6): no new sandbox, environment scrubbing or permission-file checks.
- Never write a raw IP address or port in code, specs, docs or fixtures.
- Not done if merging is reachable only from tests. The E2E must run the built CLI with a merge conflict and an integration failure.
- Do not fabricate merge results. A preflight that cannot run is a failure, not a pass.
- Do not write to `ctx.repoRoot` in this WP.
- No test-only branches in `src/`. No stub bodies.

## Out of scope
Merging into the user's branch (R3.7). Undo (R3.7). Discard (R3.7). Solo mode (R3.8). The governor.
